# filr Core CLI API Specification (v1)

This document specifies the first iteration of the **filr** command-line interface.

It is intentionally narrow in scope. It captures only the parts of the system that are currently understood cleanly:

* a single internal warehouse
* drop-level storage and export
* document inspection
* no query language yet
* no filesystem views yet
* no metadata transformation API yet
* no delete operation for drops

## 1. Motivation

The first iteration of `filr` should be small, robust, and storage-focused.

The goal is **not** to expose the full future warehouse model immediately.
The goal is to establish a clean operational foundation around:

* initializing a warehouse
* importing drops from filesystem content
* exporting drops in canonical and filesystem forms
* inspecting drops
* inspecting individual documents
* verifying integrity
* rebuilding derived warehouse state from the transaction log

The CLI shape is inspired by the conceptual split used in ZFS:

* **warehouse** commands are analogous to `zpool`
* **drop** commands are analogous to dataset/filesystem operations
* **document** commands are read-only inspection tools

This creates a clean mental model:

* the **warehouse** is the internal managed store
* **drops** are the first-class stored units
* **documents** are inspected through stable locators inside drops

## 2. Scope of v1

### Included

* single default warehouse
* warehouse initialization and health/integrity checks
* warehouse stats and transaction log
* drop import from filesystem
* drop export in canonical CAS form
* drop export in default filesystem realization
* drop listing and inspection
* document inspection by drop URL

### Explicitly excluded

* query language
* filesystem views/materializations as first-class managed objects
* metadata transformations
* transform API
* document mutation
* drop deletion
* multi-warehouse management in the CLI

## 3. Warehouse model

`filr` manages one warehouse instance by default.

### Default location

```text
~/.filr/warehouse
```

### Override

The warehouse root may be overridden by the environment variable:

```text
FILR_WAREHOUSE_ROOT
```

This is primarily useful for:

* tests
* isolated development environments
* temporary sandboxes

### Resolution order

1. `FILR_WAREHOUSE_ROOT`
2. default `~/.filr/warehouse`

The warehouse is treated as an **internal filr-managed store**.
Users do not interact with warehouse internals directly except through the CLI.

## 4. Core conceptual model

The v1 CLI is based on the following clean concepts.

### Blob

Immutable binary content.

### Document

Immutable metadata plus one blob body.

### Drop

Immutable metadata plus a collection of immutable documents.

A drop is the first-class stored unit in v1.

### Warehouse log

The ordered history of warehouse events.

In v1, this is effectively the log of drop imports and other warehouse-level operations.

### Document locator

A stable locator for documents within a drop.

In v1, this is expressed as a `drop://...` URL.

### Drop ID

A stable identifier for drops.

Format: `d_{YYYYMMDD}_{HHMMSS}_{hash8}`

Where:
* `d_` — fixed prefix
* `YYYYMMDD` — UTC date
* `HHMMSS` — UTC time
* `hash8` — first 8 hex characters of content hash

Example: `d_20260401_143211_a7c3e9f1`

The hash is computed over the canonical drop content (header + entries), making the ID deterministic for identical imports at the same timestamp.

See ADR 003 for full specification.

## 5. CLI structure

Top-level shape:

```bash
filr <noun> <verb> [args] [flags]
```

Top-level nouns:

```text
warehouse
drop
document
```

## 6. Global conventions

### Machine-readable output

Commands that print structured information should support:

```text
--json
```

This is especially important for:

* `warehouse stats`
* `warehouse log`
* `drop inspect`
* `document head`

### Exit codes

Commands should follow normal Unix CLI expectations:

* `0` = success
* non-zero = failure

Integrity and verification commands should fail non-zero if consistency checks do not pass.

### Raw vs formatted output

Commands are either:

* **machine-readable / formatted** (`--json` or human summary)
* **raw byte output** for body content

This distinction is especially important for document inspection.

## 7. Warehouse commands

## 7.1 `filr warehouse init [name]`

Initialize a warehouse at the resolved warehouse root.

### Syntax

```bash
filr warehouse init [name]
```

### Meaning

* initialize the warehouse directory structure
* create internal metadata/state
* initialize transaction log and any derived indexes/state

### Arguments

* `name` — optional warehouse name, stored as metadata only

### Notes

The name does not affect path resolution in v1.
It is descriptive metadata.

## 7.2 `filr warehouse stats`

Show warehouse summary statistics.

### Syntax

```bash
filr warehouse stats [--json]
```

### Meaning

Report high-level warehouse state, including things such as:

* warehouse root
* warehouse name if present
* number of drops
* number of documents
* number of blobs
* total storage size
* current state hash / state SHA

### Notes

“state SHA” is intended to provide a stable summary fingerprint of current warehouse state.

## 7.3 `filr warehouse check`

Run a full warehouse integrity and consistency check.

### Syntax

```bash
filr warehouse check [--json]
```

### Meaning

Verify that the warehouse is internally consistent.

This command should be strong enough that a successful run can be treated as a consistency guarantee for the warehouse.

### Checks may include

* transaction log is readable
* all registered drops are present
* drop metadata parses correctly
* entries files are readable
* all referenced blobs exist
* content-addressed blob naming matches content where required
* derived warehouse state is consistent with the transaction log

### Contract

If this command exits successfully, warehouse consistency should be guaranteed within the scope of what v1 models.

## 7.4 `filr warehouse log`

Show the warehouse transaction log.

### Syntax

```bash
filr warehouse log [--json]
```

### Meaning

Display the ordered history of warehouse events.

In v1 this is primarily:

* drop imports
* warehouse initialization
* future rebuild events if recorded

### Notes

This log is important because `warehouse rebuild` is defined to reconstruct derived warehouse state from it.

## 7.5 `filr warehouse rebuild`

Rebuild derived warehouse state from the transaction log.

### Syntax

```bash
filr warehouse rebuild
```

### Meaning

Reconstruct derived warehouse state entirely from the canonical warehouse log.

### Use cases

* recovering from partial corruption of derived indexes/state
* verifying rebuildability
* tests and reproducibility

### Notes

This command implies the design principle that:

* the transaction log is canonical
* derived state is rebuildable

## 8. Drop commands

Drops are the main semantic storage unit exposed by the v1 CLI.

## 8.1 `filr drop list`

List all drops in the warehouse.

### Syntax

```bash
filr drop list [--json]
```

### Meaning

Show all known drops.

### Typical output fields

* drop id
* creation/import timestamp
* message if present
* document count
* blob count
* size summary

### Notes

This command should remain shallow and fast.

## 8.2 `filr drop inspect <drop-id>`

Inspect one drop in detail.

### Syntax

```bash
filr drop inspect <drop-id> [--json]
```

### Meaning

Show detailed internal information about a drop.

### Typical output fields

* drop header metadata
* document count
* blob count
* total byte size
* internal storage location
* integrity/status summary
* source/import information if present

### Motivation

This is the main low-level inspection command for stored drops.

## 8.3 `filr drop fs-import`

Import filesystem content as a new drop.

### Syntax

```bash
filr drop fs-import <path> [-m MESSAGE] [-h HEADER_JSON]
```

### Meaning

Import a file or directory from the local filesystem into the warehouse as a new drop.

This command constructs a drop whose documents are derived from filesystem objects and whose metadata includes filesystem import path information.

### Arguments

* `<path>` — source file or directory to import

### Flags

* `-m`, `--message <text>` — shorthand for `--header '{"message": "..."}'`
* `-h`, `--header <json>` — additional JSON metadata merged into drop header

### Examples

```bash
# Simple import with message
filr drop fs-import ~/Downloads/taxes -m "Tax documents 2025"

# Import with structured metadata
filr drop fs-import ~/Downloads/taxes -h '{
  "message": "Tax documents 2025",
  "actor": "hhartmann",
  "tags": ["finance", "taxes"]
}'
```

### Merge behavior

If both `-m` and `-h` are provided, the message is merged into the header JSON.

### System-added fields

The following are added automatically and cannot be overridden:

* `drop_id` — generated from timestamp + content hash
* `created_at` — UTC timestamp
* `source` — set to `"fs-import"`
* `import_root` — absolute path of import source

### Semantics

* scan the source filesystem content
* construct a drop
* ingest blobs into content-addressed storage
* create drop metadata and document entries
* record the import in the warehouse log
* print the new drop id

### Filesystem import path

For filesystem imports, document lookup in v1 is based on the imported relative path within the drop.

This is what enables the `drop://...` locator scheme described below.

## 8.4 `filr drop fs-export <drop-id> <folder>`

Export a drop using the default filesystem realization.

### Syntax

```bash
filr drop fs-export <drop-id> <folder>
```

### Meaning

Export a drop in a normal filesystem-oriented form for human/tool consumption.

This export includes:

* metadata files
* a `root/` tree realization based on the document `import_path` metadata

### Intended output shape

```text
<folder>/
  header.json
  entries.jsonl        # or equivalent
  root/
    ...
```

### Notes

This is the default export for “give me this drop as ordinary files again.”

## 8.5 `filr drop export <drop-id> <folder>`

Export a drop in pure canonical CAS form.

### Syntax

```bash
filr drop export <drop-id> <folder>
```

### Meaning

Export a drop in the canonical warehouse-oriented representation.

### Intended output shape

```text
<folder>/
  header.json
  entries.jsonl        # or entries.sqlite
  blobs/
    <sha-keyed files>
```

### Notes

This is the faithful canonical export, not the user-oriented filesystem realization.

## 9. Document commands

Document commands are inspection-only in v1.

They do not modify warehouse state.

Documents are addressed via a drop URL.

## 9.1 Drop URL scheme

### Syntax

```text
drop://<drop-id>/<import-path>
```

### Example

```text
drop://d_01HXYZ/accounts/finance/invoice-2025-01.pdf
```

### Meaning

This locates a document within a drop by its imported relative filesystem path.

### Notes

This addressing scheme is natural for filesystem-imported drops.
Future non-filesystem drop types may need additional addressing modes, but this is sufficient for v1.

## 9.2 `filr document head <drop-url>`

Show formatted document metadata.

### Syntax

```bash
filr document head <drop-url> [--json]
```

### Meaning

Resolve the given document locator and print the document header metadata.

### Output

* formatted human-readable metadata by default
* machine-readable JSON with `--json`

## 9.3 `filr document body <drop-url>`

Print raw document body bytes.

### Syntax

```bash
filr document body <drop-url>
```

### Meaning

Resolve the given document locator and write the raw body bytes to stdout.

### Notes

This is a raw byte stream command and should behave well in Unix pipelines.

## 9.4 `filr document show <drop-url>`

Show metadata plus body in a human-oriented way.

### Syntax

```bash
filr document show <drop-url>
```

### Meaning

Display:

1. formatted header metadata
2. separator line
3. body content if text-like

For binary content, this command should avoid dumping unreadable binary by default and instead show a short binary summary.

### Rationale

This makes `show` safe and useful for normal interactive inspection, while `body` remains the raw byte-oriented primitive.

## 10. Canonical drop representation

The v1 CLI assumes the following canonical drop representation:

```text
drop/
  header.json
  entries.jsonl        # or entries.sqlite
  blobs/
    <sha-keyed files>
```

### `header.json`

Drop-level metadata.

### `entries.jsonl` / `entries.sqlite`

Document entries, each containing at least:

* document id
* blob reference
* document-local metadata

### `blobs/`

Content-addressed blob bodies.

## 11. Operational principles reflected in this API

This API is designed around the following principles.

### 11.1 Warehouse state is internal

The warehouse is filr-managed internal state, not a directory structure users manipulate directly.

### 11.2 Drops are the main public storage unit

The CLI is drop-centric because drop-level storage is the part of the design that is currently best understood.

### 11.3 No deletion

There is intentionally no `drop rm` command. We will not support deletions.

Maybe archival/hidden in the future.

### 11.4 Export has two distinct meanings

There is a clean distinction between:

* canonical CAS export (`drop export`)
* user-oriented filesystem export (`drop fs-export`)

### 11.5 Document inspection is read-only

Document commands are observational only.

### 11.6 Rebuildability matters

`warehouse rebuild` exists because warehouse-derived state should be reconstructible from the canonical log.

## 12. CLI summary

```bash
# warehouse
filr warehouse init [name]
filr warehouse stats [--json]
filr warehouse check [--json]
filr warehouse log [--json]
filr warehouse rebuild

# drops
filr drop list [--json]
filr drop inspect <drop-id> [--json]
filr drop fs-import <path> [-m MESSAGE] [-h HEADER_JSON]
filr drop fs-export <drop-id> <folder>
filr drop export <drop-id> <folder>

# documents
filr document head <drop-url> [--json]
filr document body <drop-url>
filr document show <drop-url>
```

## 13. Non-goals of this specification

This specification intentionally does **not** define:

* queries over warehouse contents
* transforms
* metadata editing
* versioned document lineage
* managed filesystem views
* drop deletion
* multi-warehouse management
* remote sync or federation

Those belong to later iterations.

## 14. One-sentence summary

> filr v1 is a single-warehouse, drop-centric CLI for importing, storing, exporting, inspecting, and verifying immutable drops and their documents, with rebuildable internal state and a clear separation between canonical CAS export and filesystem-oriented export.
